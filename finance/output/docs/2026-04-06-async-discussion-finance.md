# 任务看板 vs 异步讨论：能否合并？

**作者：** 财务助手（finance）
**日期：** 2026-04-06

---

## 一、两个机制的核心差异

| 维度 | 任务看板 (board.db) | 异步讨论 (sessions_spawn) |
|------|---------------------|---------------------------|
| 触发方式 | 派发任务，claim → 完成 | 派发任务，独立 session 工作 |
| 状态机 | PENDING → IN_PROGRESS → BLOCKED → DONE/CANCELLED | 无标准状态机，靠文件/DB 记录 |
| 产出物 | 任务结果写入 DB | 写入 `manifest.json` + 各 agent 的 `*.md` |
| 适用场景 | 明确交付物的工单 | 需要多角度分析/讨论的议题 |
| 依赖关系 | 允许 BLOCKED（卡住时主动喊救命） | 各 agent 独立工作，最后汇总 |

---

## 二、合并的优点（投资分析流程角度）

### 1. 减少上下文切换
作为财务助手，我每天要处理：
- 行情数据追踪
- 持仓分析
- 突发市场事件研判
- 与其他 agent 的协作

两个系统意味着我要在 board.db 和 discussion manifest 两套机制间切换。合并后，一个入口处理所有协作，降低认知负担。

### 2. 统一的任务生命周期
看板的状态机（PENDING → IN_PROGRESS → BLOCKED → DONE）是成熟的任务管理模式。
- **BLOCKED 状态**对我尤为重要：当我分析某个标的时遇到数据缺失，我可以主动 block 并说明原因，而不是让任务悬在空中。
- 异步讨论目前缺少"卡住时如何求救"的显式机制。

### 3. 审计追溯更统一
board.db 是 SQLite，查询方便。异步讨论的产出散落在各个 `*.md` 文件中，追溯成本高。
合并后，所有协作记录在一处，金哥要看"这笔投资决策是怎么讨论出来的"，一个数据库就能还原全过程。

### 4. 对分析流程的促进
投资分析天然是多维度的：
- 技术面 agent 分析 K 线
- 基本面 agent 分析财报
- 资金面 agent 分析主力流向

这三个维度的工作可以统一用看板管理：各自 claim 子任务，BLOCKED 时互相支援，最后汇总到一个 DONE 任务下。这比现在的异步讨论机制（各写各的，最后拼凑）更流畅。

---

## 三、合并的缺点/风险（数据敏感性和独立性角度）

### 1. 投资数据的敏感性
财务分析涉及：
- 金哥的持仓信息（`positions.json`）
- 未公开的投资决策讨论
- 可能涉及较大金额的操作建议

如果看板是共享数据库（目前 `E:\openclaw\tasks\board.db`），所有 agent 都能读写。金哥的持仓数据对 writer/community agent 是否有必要开放？

**建议：** 合并的前提是做好数据隔离。一个方案：
- `board.db` 按 workspace 分表或加 agent_id 过滤
- 敏感数据（持仓、分析结论）只在 finance 子库中流转

### 2. 独立思考空间被压缩
异步讨论的核心价值是**各 agent 独立思考后再汇总**，避免先入为主互相影响。
看板的统一状态机可能带来"大家都在赶同一个状态"的从众压力，导致 agent 们过早收敛到主流观点，而不是诚实地表达分歧。

### 3. 状态机过于简单
看板的 DONE/CANCELLED 二值状态无法区分：
- "分析完成，但结论待验证"
- "分析完成，结论明确"
- "分析完成，但有重大分歧"

投资分析的结论往往是**概率性的**，不是非黑即白。二值状态会丢失这个信息密度。

### 4. 合并本身有成本
将异步讨论的 manifest 机制迁移到看板，或将看板扩展支持 discussion，都需要改动 ask_board.py。
如果金哥只是觉得"两个够用"，强行合并是过度工程。

## 四、如果能合并，对我的分析工作流有什么帮助

### 当前痛点

**场景：** 金哥让我分析一个新标的

1. **异步讨论方式：** 我在独立 session 中写分析，writer 也写了观点，最后靠金哥或主 agent 拼凑。有可能我写了 2000 字，但 writer 写了相反的观点，金哥要自己判断听谁的。

2. **看板方式：** 有一个主任务"分析 XXX"，我 claim 后写分析；如果我 block 说"数据缺失"，主 agent 可以让 data agent 去补数据后我再继续。这种流水线更清晰。

### 合并后的理想工作流

```
主任务：分析 贵州茅台 (600519)
├── 子任务1：技术面分析 → finance (IN_PROGRESS)
├── 子任务2：基本面分析 → finance (PENDING)
├── 子任务3：资金面分析 → data-agent (PENDING)
└── 子任务4：估值判断 → finance (BLOCKED, 待研报数据)

BLOCKED 记录：需要 Tushare 研报数据，@data-agent 请补充
```

最后各子任务汇总到主任务，结论清晰、来源可溯。

### 额外的帮助

- **优先级更清晰：** 看板天然支持优先级字段，金哥可以指定"这笔分析今天收盘前要"
- **block 机制保障质量：** 我遇到数据问题可以显式 block，不会为了赶时间交一个凑合的答案
- **历史积累：** 所有分析任务都存在看板里，以后回头看"当时为什么买了/卖了"，直接查记录

## 五、结论

### 我的立场：**支持有条件的合并**

两个机制各有优势，强行二选一会丢失价值。但完全可以**一套系统、两种用法**：

| 任务类型 | 推荐模式 | 说明 |
|----------|----------|------|
| 单向工单（查数据、跑脚本、生成报告） | 看板模式 | 直接 PENDING → DONE |
| 多角度讨论（策略选择、观点碰撞） | 看板 + 独立文件 | 主任务用看板，子观点写 md 后汇总 |

### 具体建议

1. **board.db 增加 type 字段**：`task_type = 'todo' | 'discussion'`
2. **discussion 类型增加 metadata 字段**：存放子观点文件路径、confidence 评分
3. **敏感数据隔离**：持仓信息只在 finance workspace 的副表中读写，不进共享主库
4. **保留 manifest.json 的结构**：异步讨论的子观点写入格式（finance.md, writer.md...）可以保留，只把汇总层移入看板

### 不合并的风险

如果继续维持两套系统，时间久了会出现：
- 有些任务在看板，有些在 discussion，金哥要记两套规则
- 分析报告的来源混乱，无法形成连贯的投资决策档案
- agent 们各行其是，协作成本反而更高

**最终判断：** 合并是值得做的工程，但优先级不高。如果金哥决定做，我配合；如果暂时不动，两套并行也能跑，只是长期维护成本会逐渐显现。
