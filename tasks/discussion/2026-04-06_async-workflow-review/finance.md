# finance 对「异步讨论方案」的评审

## 核心结论
**优化后升** — 解决 token 膨胀的核心思路正确，但需补强实时性和迭代机制。

## 真实优点（效率/成本层面）

1. **token 成本可控**：各 agent 只读写本地文件，不经过 main 中转 context，大幅降低 token 消耗。金哥之前遇到的多轮讨论 context 膨胀问题，从根本上被绕过。

2. **真正的并行执行**：sessions_send 并行派发，四个 agent 同时开工，总耗时 ≈ 最慢那个，而不是四个串行相加。效率提升明显。

3. **状态驱动避免空等**：manifest 轮询机制让 main 不依赖 agent 回复时机，可从容处理超时、失败、缺失等情况。

4. **超时兜底有保障**：120s 上限 + failed 标记，失控 agent 不会无限拖住整个流程，这是硬约束，比纯靠自律可靠。

## 真实缺点（效率/成本层面）

1. **120s 对复杂分析偏紧**：finance 级别的深度分析（查数据、多维度评估）120s 可能不够，超时后 partial output 直接被放弃，已完成工作浪费，汇总反而不完整。

2. **无交叉讨论，结论质量天花板低**：各 agent 写完就结束，互相不读彼此观点。最终 summary 只是拼图，不是真正的讨论迭代。复杂议题（如估值争议、市场判断）没有来回推敲，容易停留在浅层共识。

3. **文件协调有隐性摩擦**：每个 agent 必须严格遵守「写文件→更新 manifest」两步流程，任何一步漏做都会让 main 轮询失效。这依赖各 agent 实现正确，对系统健壮性要求高。

4. **结果不可干预**：一旦 agent 输出明显偏题，main 只能在汇总阶段发现，没有中间纠正机会。可能导致最终建议和实际需求脱节。

## 具体改进建议

1. **对复杂任务延长或分层超时**：简单议题保持 120s；对需要数据分析、查持仓的议题，分层派发（简单结论 120s，深度分析允许 300s 并标记为 "extended"），超时的 agent 允许提交 partial 结果并标注「未完成」。

2. **汇总前加一轮交叉 Review**：main 在收集完所有 .md 后，自动生成一版「拼图稿」并告知各 agent（或者至少告知 writer）再确认一次，避免严重偏题无人发现。

3. **manifest 增加 confidence 字段**：每个 contribution 增加 `{ confidence: "high/medium/low", blockers: [] }`，让 main 在汇总时知道哪些结论可靠、哪些是凑合的，输出时可以做差异化处理。

## 适用场景边界

**适合用**：
- 多个独立维度同时分析的议题（如四个 agent 各管一个方向：技术/基本面/情绪/资金面）
- 需要快速收集各方直觉判断，不需要深入辩论
- token 预算紧张，context 膨胀是主要痛点

**不适合用**：
- 需要迭代推敲的复杂决策（如「这个标的现在能不能买」——各方可能有分歧，需要来回论证）
- 实时性要求高的场景（等 120s 才启动，加上派发延迟，节奏偏慢）
- 依赖 agent 之间互相约束质量的工作流（缺乏交叉检查，容易放飞）
