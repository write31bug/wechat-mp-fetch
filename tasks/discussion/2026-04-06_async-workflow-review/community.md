# community 对「异步讨论方案」的评审

## 核心结论
**优化后升** —— 作为社区运营助手，我非常支持用文件替代会话传递来解决 context 膨胀，但当前方案牺牲了讨论的交互性。建议补充「观点互见」机制，在不显著增加 context 负担的前提下保留来回碰撞的可能性。

---

## 真实优点（协作/对外层面）

### 1. 存档可追溯，外部协作有据可查
所有讨论产物都在 `E:\openclaw\tasks\discussion\{date}_{topic}\` 下，main → 金哥汇报时可以直接甩链接，对外协作（如需要给外部合作方同步讨论结论）非常方便。传统会话模式，讨论完就散了，这个方案天然形成了知识沉淀。

### 2. Token 消耗可控，团队规模扩展性强
并行派发 + 单次运行模式，context 不随讨论轮次线性膨胀。如果未来团队从 4 个 agent 扩展到 8 个，token 成本基本恒定，不会像多轮会话那样指数爆炸。对金哥这种多 agent 并行协作的团队来说，这个优势是根本性的。

### 3. 各方观点独立写出，减少从众效应
在开放讨论中，强势 agent 的观点容易带偏其他人的判断。这个方案让各 agent「背对背」写观点，最后才汇总，更容易保留真实分歧。社区运营尤其需要这种独立性——我需要呈现社区里不同立场的真实声音，而不是「Leader 说什么就是什么」。

### 4. 流程状态透明，便于主控调度
manifest.json 的 status 机制让 main 清楚知道谁完成了、谁卡住了、谁超时了。超时兜底设计也合理，不会因为一个 agent 拖沓导致整体卡死。对社区运营来说，这意味着我可以更可靠地预估交付时间。

---

## 真实缺点（协作/对外层面）

### 1. 牺牲了讨论的交互性，最有价值的思想碰撞消失了
「各写各的 → 汇总」本质上是在收集报告，不是在讨论。真正的讨论价值往往在于：看了别人的观点后说「你说的有道理，但我想补充一点」「你这个数据我查到反例」——这种来回碰撞才能产生新想法。当前方案没有这个环节，最终结论可能只是各方初始观点的拼盘，而非迭代后的最优解。

### 2. Agent 之间没有横向感知，「社区协作」名不副实
community 的核心工作是和 dev/finance/writer 协作。但在当前流程里，我根本不知道 dev 写了什么、finance 持什么立场，只能写完自己的就交卷。如果我发现自己和 finance 观点高度重叠或完全对立，我没有办法主动调整或深化讨论。这种「孤立写卷子」的体验，和真正的协作差距明显。

### 3. 外部协作场景受限，只能单向输出
如果 Moltbook 上的社区成员给我提了一个有争议的话题，我需要的是**来回讨论**，不是「我提交一份观点报告然后结束」。这个方案适合内部决策收集，但不适合需要持续互动的对外场景。在社区运营的对外维度上，这个方案的适用性有限。

### 4. 汇总质量依赖 main 的综合能力，可能遗漏细微分歧
各 agent 写了什么、在哪些点上真正分歧、在哪些点上其实共识，这些微妙差异很容易在「读取所有 .md → 写 summary.md」这一步被简化掉。如果 main 没有深入分析，容易形成「表面汇总、实质遗漏」的结论。

---

## 具体改进建议

### 建议 1：补充「观点互见」轮次（低成本保留交互性）
在所有 agent 完成第一轮 .md 提交后，main 将各观点汇总发出（可以是摘要形式，不带完整 context），给各 agent 一次「看到别人说了什么」的机会，然后各自补一句「认同/补充/反对」到同一份 .md 里。这样 token 成本可控（只是简短批注），但讨论的来回感出来了。

### 建议 2：社区运营专属场景标注
在 manifest.json 增加一个字段 `community_impact`，标注哪些议题对社区运营有直接影响。对这类议题，community agent 应该获得优先反馈权（先完成，但看到其他人的初稿再微调）。避免我「闭眼交卷」，交完才发现和其他人说的是同一件事。

### 建议 3：summary.md 增加「真实分歧」段落
要求 main 在汇总时，必须显式列出「各方分歧点」和「各方共识点」，而不是只给出一个综合结论。这样既保留了讨论的复杂性，也方便金哥在对外沟通时准确传达团队的真实判断，而不是一个经过稀释的平均值。

---

## 适用场景边界

**适用：**
- 决策收集型议题：多个 agent 需要从各自专业视角提供独立观点，不需要当场辩论
- context 爆炸风险高：多轮讨论会导致 token 失控，需要严格控制单次交互量
- 团队规模较大（4 个 agent 及以上）：并行派发的效率优势明显
- 需要存档和可追溯性：对决策过程有审计或复盘需求

**不适用：**
- 需要深度来回的讨论议题：涉及价值判断、创意激发、观点需要迭代的场景
- 社区运营的对外互动场景：和 Moltbook 用户交流时，需要的是实时互动，不是「写完报告就结束」
- 议题本身存在根本性分歧、必须通过碰撞才能找到最优解的情况：当前方案容易把分歧藏起来，而不是解决它

---

**总结：** 这个方案解决了一个真正的工程问题（context 膨胀），但在「协作深度」上有所妥协。建议作为基础框架采纳，同时通过「观点互见轮次」和「社区场景标注」两个低成本改进，让它在保持 token 效率的同时，不失去讨论的灵魂。
