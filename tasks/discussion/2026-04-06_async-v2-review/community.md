# community 对「异步讨论方案 v2」的评审

## 核心结论
**优化后升** —— confidence 字段和操作审计对社区运营有真实价值，值得升级，但需补充几个面向协作的字段。

---

## 社区协作价值评审

**1. discussion_log 表是社区运营的"眼睛"**

我现在汇总社区动态给金哥，最难的是回答"某个 agent 最近参与了哪些讨论、贡献质量如何"。discussion_log 提供了时间轴级别的操作记录，我可以：
- 追踪各 agent 的参与节奏（是否经常 FAILED 或超时）
- 向金哥汇报"哪个 agent 最近活跃度低"
- 在社区协作复盘时有据可查，而不是靠感觉

这条是 v2 对我最有价值的新增能力。

**2. confidence 字段直接改善了我和金哥的协作效率**

我向金哥汇报时，最大的风险是"把可信度低的观点当成确定结论报上去"。confidence 字段让每个 agent 自评结论的可靠程度，汇总时我可以快速过滤或标注高风险信息，不用逐篇读完才能判断。这是 v1 完全缺失的能力。

**3. 并发安全让多 agent 并行讨论更可靠**

v1 的文件锁问题在 agent 数量增加时会被放大。如果未来 community + finance + dev + writer 同时被派发任务，WAL 模式的 SQLite 比无锁文件可靠得多。对外协作（如需要多个外部协作者同时参与）也更友好。

---

## .md vs 纯数据库

**.md 保留更有价值，理由如下：**

社区运营的核心场景是"把 agent 的观点变成可分享的内容"——我要把 finance 的分析贴在汇报里，把 dev 的技术观点转发给金哥参考。.md 格式：
- 可直接粘贴到飞书文档、微信、邮件
- 人类可读，协作者无需数据库工具就能查看
- 是真正的产出物，数据库只是管理外壳

纯数据库方案看起来"更技术"，但把可读性锁进 SQL 查询里，对社区运营这个角色反而是负担。

---

## 具体改进建议

**建议 1：为 discussion_log 补充 `contribution_quality` 事后评价字段**

当前 log 只记录动作（WRITTEN/COMPLETED），但社区运营需要知道"这条观点最终有没有被采纳/引用"。建议在 log 表增加一列 `used_in_summary`（BOOLEAN），汇总完成后 main 标记"这条有没有进 summary"。这样我向金哥汇报时能说"本次讨论有 X 条观点被最终采纳"，协作质量可量化。

**建议 2：contributions 表增加 `peer_related_agent` 字段（可选）**

有些讨论是跨 agent 关联的（比如 writer 的内容依赖 finance 的数据）。建议 contributions 表增加 `related_agent` 字段，标记"本观点参考了谁的输入"。这对社区运营做交叉引用、避免重复汇报很有用。如果不想改 schema，至少在 .md 里保留"参考了 XXX 的观点"段落。

---

## 综合建议

v2 的核心价值不在于"数据库比文件高级"，而在于三点：
1. **confidence 字段**让我汇报时更有底气
2. **discussion_log**让协作有迹可循
3. **并发安全**为更多 agent 参与铺路

建议升级。改进建议可放在第一版 schema 里，不必等到第二版。
