# 任务看板 vs 异步讨论：能否合并？

**作者：** dev（开发助手）  
**日期：** 2026-04-06  
**议题：** 任务看板与异步讨论机制能否合并为一套系统

---

## 一、两个机制的核心区别

| 维度 | 任务看板 | 异步讨论 |
|------|---------|---------|
| **核心用途** | 任务分发、执行追踪 | 多角度观点收集、并行调研 |
| **触发方式** | 主 agent 派活，subagent claim | sessions_spawn 广播式派发 |
| **状态机** | PENDING → IN_PROGRESS → BLOCKED → DONE/CANCELLED | 独立 session，无统一状态 |
| **产出物** | 代码/文件 + 状态流转 | 观点文档 + confidence 标注 |
| **阻塞处理** | BLOCKED 状态 + 求助机制 | 120s 超时后 FAILED |
| **适用场景** | 有明确交付物的任务 | 开放式讨论、方案调研 |

---

## 二、合并的优点

### 1. 统一入口，减少心智负担
金哥只需要记「有一个任务系统」，不用区分"这是看板任务还是讨论任务"。

### 2. 状态机统一，追踪更清晰
讨论也是一种任务。合并后，金哥能在一个看板上看全局进度，不用分别查两个地方。

### 3. 资源复用
- 底层只需一套数据库 schema
- ask_board.py 等 Python 模块只维护一份
- 降低多套系统维护的出错概率

### 4. BLOCKED 机制可复用
看板的 BLOCKED → 求助机制，其实和讨论的超时 FAILED 是同一语义（"我搞不定了"）。合并后可以统一处理。

### 5. 有利于后续扩展
如果以后要加「任务优先级」「截止时间」「分类标签」等，一套系统比两套好扩展。

---

## 三、合并的缺点/风险

### 1. 语义混淆风险
「任务」和「讨论」本质不同：
- **任务**：有明确交付物，结束时需要 `block_task` + `complete_task` 双保险
- **讨论**：输出观点，状态是 DONE/FAILED，核心字段是 `confidence`

强行合并后，一个统一的 `status` 字段能否同时表达这两种语义？需要设计层面的权衡。

### 2. 讨论的「并行收集」特性会丢失
异步讨论的核心是**多个 agent 独立同时工作**，最终汇总。金哥在 manifest 里定义好话题，各 agent 互不打扰地写观点。

如果合并到看板，按现有状态机，一个任务同时只能有一个 agent 在处理（IN_PROGRESS）。除非改状态机支持「待领取 + 多人并行」，这就不是简单合并了。

### 3. confidence 字段的归属问题
讨论产出的 `confidence`（high/medium/low）是观点质量的元数据。如果合并，任务产出的 `next_step` 和讨论产出的 `confidence` 如何共存？或者其中一个变成可选字段？这需要 schema 变更。

### 4. manifest.json 这类讨论元数据的处理
讨论任务有独立的 manifest（包含背景、目标、参与者），这是看板任务没有的。如果合并，这部分信息是作为任务的 description 字段，还是加一个新字段？

### 5. 历史包袱
如果已经有很多讨论记录和看板任务数据，迁移成本不容忽视。

## 四、如果能合并：系统架构草图

```
┌─────────────────────────────────────────────────────┐
│                    统一任务表 tasks                  │
│  ┌─────────┬──────────┬─────────┬────────┬───────┐  │
│  │   id    │  type    │ status  │ result │ meta  │  │
│  ├─────────┼──────────┼─────────┼────────┼───────┤  │
│  │   1     │  TASK    │ DONE    │ {...}  │ next_ │  │
│  │   2     │  TASK    │ BLOCKED │ {...}  │ next_ │  │
│  │   3     │ DISCUSSION│ DONE   │ {...}  │ conf. │  │
│  └─────────┴──────────┴─────────┴────────┴───────┘  │
│                                                     │
│  type = 'TASK'     →  保留现有看板逻辑               │
│  type = 'DISCUSSION' →  并行派发 + confidence       │
└─────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
     ┌──────────────┐               ┌──────────────┐
     │   ask_board  │               │ask_discussion│
     │  create_task │               │ create_disc.  │
     │  claim_task  │               │ parallel_     │
     │  block_task  │               │   spawn       │
     │ complete_task│               │ update_contri.│
     └──────────────┘               └──────────────┘

        高层接口统一：
        create_task(type='TASK', ...)      → 派发任务
        create_task(type='DISCUSSION', ...) → 发起讨论
        底层共享同一张表，type 决定业务逻辑差异
```

**关键设计点：**

1. **type 字段区分业务类型**，不影响状态机流转
2. **meta JSON 列**：TASK 存 `next_step`，DISCUSSION 存 `confidence` + `contributors`
3. **并行讨论**通过 `type=DISCUSSION` + `spawn multiple agents` 实现，不依赖 IN_PROGRESS 独占
4. **共用 ask_board.py**，内部根据 type 分发到不同处理逻辑

---

## 五、结论

**可以合并，但需要结构性重构，不是简单叠加。**

两个机制的共同点（状态流转、统一的数据库）是合并的基础。但差异点（并行 vs 串行、confidence vs next_step、manifest 元数据）决定了合并后的 schema 必须比现有看板更复杂。

**推荐路径：**
1. **短期**：保持两套系统并存，在 ask_board.py 层做语义统一（让 create_task 能同时支持两种模式）
2. **中期**：将 schema 升级为 type + meta JSON，支持两套业务逻辑共存于同一张表
3. **长期**：如果并行讨论场景频繁，可以考虑把「并行多 agent」做成 first-class 概念，融入任务系统

**核心原则：合并是为了减少金哥的心智负担，不是为了合并而合并。如果合并后反而需要记住更多细节，就不值得。**
