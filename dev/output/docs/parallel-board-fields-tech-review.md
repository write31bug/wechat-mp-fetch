# 并行看板字段技术审查报告

> 审查人：dev  
> 依据：writer/parallel-board-fields-draft.md  
> 结论：7 个字段整体设计合理，局部有技术挑战和安全风险，以下逐字段说明。

---

## 逐字段评估

### 1. depends_on

**数据类型：JSON 数组（任务 ID 列表）**

#### 技术挑战

| 风险 | 说明 | 建议 |
|---|---|---|
| **循环依赖校验** | 检测有向图循环需要 DFS，时间复杂度 O(V+E)，任务量大时须建索引 | 写入时触发校验，检测到循环时返回错误并拒绝写入 |
| **依赖链深度** | 多层嵌套依赖（A→B→C→D）校验逻辑递归，若无深度限制可能爆栈 | 设置最大依赖深度（如 10 层），超深拒绝 |
| **SQLite JSON 存储** | 数组存为 TEXT 类型（`json1` 扩展支持查询），但无法建 B-Tree 索引 | 若后续需要"查询所有依赖我的任务"（反向查询），建议改为中间表，不宜全押 JSON |
| **并发修改** | 两个任务同时添加互相依赖，在并发场景下可能绕过校验 | 写入时加事务锁（SQLite 默认串行写入，外围高并发需评估） |

**结论：有挑战但可实现。** 核心风险是循环校验和反向查询性能，建议优先保证单字段 JSON 方案可行，复杂反向查询留待后续优化。

---

### 2. blocked_by

**数据类型：JSON 数组（任务 ID 列表）**

#### 技术挑战

与 `depends_on` 基本一致，额外关注：

| 风险 | 说明 |
|---|---|
| **状态联动时序** | 任务从 BLOCKED 解除时清空 blocked_by，但清空操作和状态变更须在同一事务内，否则并发修改可能丢数据 |
| **历史记录缺失** | 草案提到"或保留历史记录"，若要保留则须单独建 `blocked_by_history` 表，否则无法追溯谁阻塞了多久 |

**结论：比 depends_on 简单。** 无循环依赖问题（blocked_by 是描述性快照，不参与调度），但状态联动须保证原子性。

---

### 3. priority

**数据类型：枚举整数（0–4）**

#### 技术挑战

无实质挑战。枚举存储为 TINYINT/INTEGER，索引友好，调度层取值直接比较。

唯一注意：P0 任务的"优先获得资源"策略需要在调度层单独处理，不影响数据库设计。

**结论：最简单，无风险。**

---

### 4. due

**数据类型：ISO 8601 日期时间字符串**

#### 技术挑战

| 风险 | 说明 |
|---|---|
| **时区歧义** | `"2026-04-10 18:00"` 不带时区，跨地区协作时解释不一致 | 必须强制带时区偏移（`+08:00` 或 `Z`），存储推荐 UTC |
| **逾期检测频率** | 界面显示"已逾期"需要轮询或定时任务，若在数据库层做（如 `WHERE due < NOW()`）须注意时区函数支持 | SQLite 无原生时区函数，建议存储 UTC 时间戳（INTEGER/REAL），Python 层做转换 |
| **截止日期早于依赖满足时间** | 草案已说明是软约束，不影响调度，无需改造 |

**结论：有陷阱但可控。** 推荐存储为 UTC UNIX 时间戳（INTEGER），Python 层负责格式化和时区转换，界面展示时转本地时间。

---

### 5. stage

**数据类型：枚举字符串**

#### 技术挑战

无实质挑战。存储为 TEXT，外键关联 stage 表（id, name），或者简单用 CHECK 约束限制合法值。

**结论：无风险，最干净的字段。**

---

### 6. handoff_notes

**数据类型：自由文本字符串**

#### 安全风险 ⚠️

| 风险 | 级别 | 说明 |
|---|---|---|
| **XSS** | **高** | handoff_notes 可能包含 HTML（如粘贴的 Figma 链接、代码片段），若直接渲染到 DOM 而未转义，可执行恶意脚本 |
| **存储放大** | 低 | 无最大长度限制时，单条任务可能写入数 MB 文本，影响数据库和传输 |

**建议：**
- 字段加最大长度约束（草案已建议 2000 字符，建议进一步限制为 4000）
- 输出时强制 HTML 转义（Python: `html.escape()` 或 Jinja2 autoescape）
- 若需要支持富文本，引入白名单标签过滤（如 `bleach` 库只允许 `<a><code>`）

**结论：有安全隐患，必须在渲染层做转义或过滤。**

---

### 7. deliverable

**数据类型：JSON 数组（对象列表）**

#### 技术挑战

| 风险 | 说明 |
|---|---|
| **嵌套 JSON 复杂度** | 每个元素是 `{"name": "", "link": "", "status": ""}` 结构，link 字段需要校验 URL 格式，否则可写入任意文本 |
| **强制校验触发时机** | "DONE 前强制全部 deliverable done" 需要在状态流转逻辑中嵌入校验，若任务被强制标记 DONE（管理员操作），可能导致数据不一致 | 建议此校验为可配置的策略字段（见待确认问题 2），非硬编码 |
| **JSON 部分更新** | 更新单个 deliverable 的 status 需要 patch 操作，若直接 overwrite 可能丢并发修改 | 建议原子更新中间表记录，而非 patch JSON 字段 |

**结论：有挑战但中等。** 若 deliverable 使用频率高（频繁标记单个交付物状态），建议拆为独立表而非 JSON 数组。

## 安全总评

| 字段 | XSS 风险 | 数据注入风险 | 隐私风险 |
|---|---|---|---|
| depends_on | ✅ 无 | 低（仅校验任务 ID 存在性） | 无 |
| blocked_by | ✅ 无 | 低 | 无 |
| priority | ✅ 无 | 无 | 无 |
| due | ✅ 无 | 无 | 无 |
| stage | ✅ 无 | 低 | 无 |
| handoff_notes | ⚠️ **有** | 中（超长文本） | 低 |
| deliverable | ⚠️ **有**（link 字段） | 中（非法 URL） | 无 |

**结论：handoff_notes 和 deliverable.link 是主要风险点，须在渲染层做输出过滤。**

## 附录：待确认问题技术意见

### Q1: depends_on 硬拦截 vs 软提示？

**建议：硬拦截。**

软提示（警告但不阻止）会导致任务实际状态与看板承诺不一致，且调度层不得不处理"依赖未满足但任务在 IN_PROGRESS"的边界情况，大幅增加状态机复杂度。

硬拦截的好处：
- 状态机是唯一真相来源，无歧义
- 实现简单，校验函数返回 True/False 即可
- 不会出现"幽灵 IN_PROGRESS"任务

若担心误操作体验，可以区分"新建时提示"和"claim 时拦截"两个层级，但核心流转必须是硬拦截。

---

### Q2: deliverable 是否开启 DONE 前强制全部完成校验？

**建议：作为看板级别的配置开关，默认为 OFF。**

原因：
- 交付物粒度不一定和任务完成时机对齐（如"写文档"任务，交付物是文档链接，但任务已可标记 DONE）
- 强制校验会拖慢日常流程，尤其在快速迭代阶段
- 提供开关让团队自己决定是否开启，比一刀切更灵活

若开启，建议在 `board_config` 表中存储此策略：
```sql
ALTER TABLE board_config ADD COLUMN enforce_deliverable_done BOOLEAN DEFAULT 0;
```

---

### Q3: blocked_by 与 depends_on 是否合并？

**建议：不合并。**

两个字段语义确实有重叠，但使用场景不同：

| | depends_on | blocked_by |
|---|---|---|
| 核心语义 | 前置条件未满足（内部、可控） | 外部卡点（外部、不可控） |
| 调度影响 | 硬拦截状态推进 | 仅描述性 |
| 填写时机 | 任务创建时规划 | 阻塞发生时动态填写 |
| 清空时机 | 依赖完成后自动失效 | BLOCKED 解除时需手动或自动清空 |

合并为一个字段会丢失这个语义区分。若担心字段过多，可以用 JSON 数组统一存，但字段命名须区分（`dependencies` vs `blockers`）。

---

### Q4: handoff_notes 已读确认是否需要审计记录？

**建议：需要，但记录在独立表。**

`handoff_notes` 是交接信息，审计是交接动作，两者是不同实体。建议：

```sql
CREATE TABLE handoff_audit (
  id INTEGER PRIMARY KEY,
  task_id TEXT NOT NULL,
  from_user TEXT NOT NULL,
  to_user TEXT NOT NULL,
  read_at DATETIME,       -- NULL 表示未读
  read_ip TEXT,            -- 可选，记录读取 IP
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

审计表记录的是"谁在什么时候读了/没读"，而不是 notes 内容本身。notes 变更仍然记录在任务表的 `handoff_notes` 字段中。

---

## 总结

| 字段 | 技术风险 | 安全风险 | 实现优先级 |
|---|---|---|---|
| depends_on | 中（循环校验、JSON 查询） | 无 | P1 |
| blocked_by | 低（事务原子性） | 无 | P2 |
| priority | 无 | 无 | P3 |
| due | 中（时区处理） | 无 | P2 |
| stage | 无 | 无 | P3 |
| handoff_notes | 低（长度约束） | **高（XSS）** | P1（安全先行） |
| deliverable | 中（JSON patch） | 中（link XSS） | P2 |

**最大技术风险：** depends_on 的循环依赖校验 + SQLite JSON 反向查询性能。  
**最大安全风险：** handoff_notes 和 deliverable.link 的 XSS，建议渲染层统一做 HTML 转义或白名单过滤。  

整体方案可行，建议优先处理安全（handoff_notes 转义）和核心调度（depends_on 校验）两部分。
