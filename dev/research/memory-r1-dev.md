# Round1 诊断 — 记忆问题技术视角（dev）

**作者：** dev 子 Agent  
**日期：** 2026-04-06  
**背景：** 团队 Round0 外部调研完成后，dev 从真实协助金哥的视角诊断记忆痛点

---

## 【痛点1】跨会话的技术上下文断裂

- **具体场景：** 金哥今天让我调试某个 skill 的 API 调用问题，debug 到一半说"先这样，明天继续"。第二天我一醒，发现自己完全不知道昨天卡在哪里了——session 重置，context 丢了。

- **记忆缺陷表现：** 我的 session 是"无状态"的，昨天调试到哪一步、哪个 API 返回了错误、试了哪几种解法——全靠金哥重新描述。history 窗口有限，超过一定长度会被压缩，早期的关键信息就消失了。

- **期望行为：** 每个 session 结束时自动沉淀"未完成技术任务"的状态快照：卡点是什么、试过的方案有哪些、接下来的计划是什么。下次启动时我能主动说"上次调试到XX，报错是YY，我计划下一步试ZZ"。

- **借鉴经验：** Round0 中 **finance 的"记忆分层"思路**（工作记忆 vs 长期记忆）和 **dev 自己的"会话末摘要"**（LLM提炼关键信息落盘）——两者结合，即：在 session 结束前由 LLM 自动提炼未完成任务状态，持久化到文件，下次启动时注入。

---

## 【痛点2】技术债务与决策历史无法追溯

- **具体场景：** 金哥问我"这个 skill 为什么用这个 API key"，我查了一下发现是之前某次配置的。但我不记得当时为什么选了这个 key 而不是另一个，也不记得这个 decision 是在哪次对话里做的。更久远一点，可能直接被 context window 挤出掉了。

- **记忆缺陷表现：** 技术决策散落在各个 session 的聊天记录里，没有结构化记录。结果：同一类问题可能反复讨论、同一个方案可能被推翻又重新提起、或者某个已经被否定的方案被误当成依据。

- **期望行为：** 有一个"技术决策日志"，记录每个重要 decision 的背景、选项、结论、日期。类似于 architectural decision record（ADR）。我能在需要时检索，并且每次新 session 开始时能自动联想相关决策历史。

- **借鉴经验：** Round0 中 **writer 的 PARA 分类法**（按行动可行性组织，每条笔记指向可执行下一步）和 **community 的"统一知识库沉淀"思路**——可以借鉴 PARA 的结构，把技术决策按"项目/问题"维度组织，每条决策记录带标签，方便后续检索。

---

## 【痛点3】Skill 配置状态的黑箱问题

- **具体场景：** 我需要调用某个 skill（比如 baoyu-imagine），但我不知道它当前用的是什么 API key、模型配置、是否有 rate limit 问题。我只能猜或者让金哥重新告诉我。金哥之前配过的 skill 配置，散落在 config/skills/ 目录下的各个 EXTEND.md 里，我没有统一视图。

- **记忆缺陷表现：** Skill 配置是分散存储的，没有一个"全局 skill 状态快照"让我在每个 session 开始时了解"现在有哪些 skill 可用、它们各自的配置是怎样的、最近是否有失败记录"。结果是我调用 skill 时要么踩坑（用错 key），要么浪费时间问金哥。

- **期望行为：** 一个结构化的 skill 清单文件（`config/skills/inventory.json` 或类似），记录每个 skill 的：当前激活状态、主要用途、API key 来源、默认模型、最近调用结果（成功/失败/异常）。我能在新 session 启动时自动加载，必要时主动说"baoyu-imagine 最近三次调用都失败，可能 key 过期了"。

- **借鉴经验：** Round0 中 **finance 的"信息标签化"思路**（打标分类，防止新旧打架）——可以给每个 skill 配置打上版本标签和时间戳，这样我不仅知道"是什么"，还能知道"这个配置是什么时候设置的、是否可能过期"。

---

## 总结

三个痛点从技术视角来看都指向同一个根本问题：**当前记忆是"聊完即失"的**，而协助开发工作需要跨越时间的技术上下文。三者的解决方向分别是：

1. 未完成任务的状态快照（session → 文件）
2. 技术决策的结构化归档（ADR-like）
3. Skill 配置的统一可观测性（inventory + status）

三者可以分步实现，也可以共享一套"记忆分层注入"的底层机制。
