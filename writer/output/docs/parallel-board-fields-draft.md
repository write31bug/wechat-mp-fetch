# 并行看板字段定义草案

> 状态机：PENDING → IN_PROGRESS → BLOCKED → DONE / CANCELLED  
> 本草案为讨论初稿，待 dev 确认技术约束后修订。

---

## 1. depends_on（依赖关系）

**中文含义：** 本任务依赖的前置任务列表。

**数据类型：** 列表（数组），元素为任务 ID（字符串）。

**取值范围：** 当前看板中任意任务的 ID，允许为空。

**行为约束：**

- 选填，不强制填写。
- 填写时，被依赖的任务 ID 必须存在于看板中，否则校验不通过。
- **调度约束（核心）：** 任一依赖任务未达到 DONE 状态时，本任务不允许推进到 IN_PROGRESS（即调度层会拦截并报错）。
- 允许填写多个依赖，逻辑为"全部满足"（AND），即所有依赖都 DONE 后才解锁。
- 依赖关系不允许循环引用（A 依赖 B，B 依赖 A），建链时须校验。

**举例：**

- 任务 B 的 `depends_on` 填写 `["A"]`，则任务 A 未 DONE 之前，任务 B 无法被 claim 进入 IN_PROGRESS，调度层返回"依赖未完成"错误。
- 任务 C 依赖 A 和 B，`depends_on` 填写 `["A", "B"]`，须 A、B 均 DONE 后才解锁。

## 2. blocked_by（阻塞原因）

**中文含义：** 当前任务被阻塞的原因任务列表。

**数据类型：** 列表（数组），元素为任务 ID（字符串）。

**取值范围：** 当前看板中任意任务的 ID，允许为空。

**行为约束：**

- 选填。
- 当任务状态为 BLOCKED 时，**建议**填写本字段，记录是哪个任务导致的阻塞（可以是外部 blockers，或内部前置条件未满足）。
- 填写后，被阻塞的任务持续显示 blocked_by 中的任务 ID，方便快速定位卡点。
- 当任务脱离 BLOCKED 状态时，blocked_by 应清空（或保留历史记录，视产品需求而定）。
- blocked_by 与 depends_on 有重叠语义但使用场景不同：depends_on 更多用于"前置准备未就绪"的静默等待，blocked_by 更多用于"主动标记外部卡点"的显式阻塞。

**举例：**

- 任务 A 等待外部设计稿，状态为 BLOCKED，`blocked_by` 填写 `["外部设计稿任务ID"]`，看板界面可显示"A 被外部设计稿阻塞"。
- 外部问题解决后，将任务 A 状态改为 IN_PROGRESS，blocked_by 清空。

## 3. priority（优先级）

**中文含义：** 任务的相对紧急程度，用于调度排序和资源倾斜参考。

**数据类型：** 枚举整数（或枚举字符串）。

**取值范围：**

| 值 | 语义 |
|---|---|
| 0 | 无优先级（默认） |
| 1 | P0（最高，阻断性问题） |
| 2 | P1（高，紧急） |
| 3 | P2（中） |
| 4 | P3（低） |

**行为约束：**

- 选填，默认值为 0（无优先级）。
- P0 任务在并行调度时可优先获得资源（具体策略由调度层决定）。
- 高优先级任务阻塞低优先级任务时，可考虑优先解除阻塞。
- 建议看板视图支持按 priority 排序或高亮。

**举例：**

- 线上故障修复任务标记为 P0，无论 depends_on 是否满足，调度层可考虑优先处理。
- 日常优化任务标记为 P3，不影响正常并行调度。

---

## 4. due（截止日期）

**中文含义：** 任务的计划完成时间。

**数据类型：** 日期时间（ISO 8601 格式，建议存储为 UTC，界面展示时区转换）。

**取值范围：** 任意有效日期时间，允许为空（无截止日期）。

**行为约束：**

- 选填。
- 建议格式：`YYYY-MM-DD` 或 `YYYY-MM-DDTHH:mm:ss`，时区须明确。
- 截止日期早于当前时间时，界面可显示"已逾期"状态（但不影响状态机流转）。
- 截止日期可与调度层联动：当剩余时间不足且任务仍未 IN_PROGRESS 时，可触发提醒（具体提醒机制待定）。
- 与 depends_on 结合时，截止日期是"软约束"，依赖未满足时仍优先满足 depends_on。

**举例：**

- `due` 填写 `"2026-04-10T18:00:00+08:00"`，截止日期为 2026-04-10 下午 6 点（北京时间）。
- 截止日期已过但任务仍在 PENDING，界面显示逾期标签，调度层不自动干预。

---

## 5. stage（阶段/里程碑）

**中文含义：** 任务所属的开发阶段或里程碑，用于横向切分并行任务属于哪个工作区间。

**数据类型：** 枚举字符串。

**取值范围：**（以下为示例，可按团队实际阶段调整）

| 值 | 语义 |
|---|---|
| `planning` | 计划阶段 |
| `development` | 开发阶段 |
| `review` | 评审阶段 |
| `testing` | 测试阶段 |
| `deployment` | 部署阶段 |
| `post-launch` | 上线后/维护阶段 |

**行为约束：**

- 选填，默认值为空（表示未分类）。
- stage 是**描述性标签**，不触发状态机强制流转。
- 看板视图可按 stage 分组展示，方便识别"当前并行任务分布在哪些阶段"。
- stage 可与 priority、due 联动：高 stage（如 deployment）但低 priority 的任务可在视图中降权显示。

**举例：**

- 前端开发任务 `stage` 填写 `"development"`，后端联调任务 `stage` 填写 `"integration"`。
- 看板按 stage 分组后，可直观看到"development 阶段有 5 个任务并行，review 阶段有 2 个任务等待"。

## 6. handoff_notes（交接说明）

**中文含义：** 任务在状态变更或责任人变更时，需要告知下一接手方的关键信息。

**数据类型：** 自由文本（字符串），建议限制最大长度（如 2000 字符）。

**取值范围：** 任意字符串，允许为空。

**行为约束：**

- 选填。
- **写入时机（建议）：**
  - 任务状态从 PENDING → IN_PROGRESS 时，claim 前建议填写。
  - 任务被阻塞（进入 BLOCKED）时，填写阻塞原因供后续接手人参考。
  - 任务完成（DONE）时，填写简要结果说明。
  - 责任人变更时，旧负责人须填写交接说明，新负责人须确认已读（或至少可查）。
- 界面应在任务详情页显眼位置展示 handoff_notes。
- 交接说明不参与调度约束，但会影响协作效率。

**举例：**

- 任务从 A 转给 B，`handoff_notes` 填写 `"已完成接口设计，数据库表结构在 notion，请接着写 CRUD 接口，接口文档链接：..."`，B 接手后可直接开始，无需额外沟通。

## 7. deliverable（交付物）

**中文含义：** 任务完成后对外输出的具体成果物，用于明确"做完的定义（Definition of Done）"。

**数据类型：** 列表（数组），每个元素为交付物描述字符串；或结构化对象（含名称、链接、状态）。

**取值范围：** 任意字符串（描述），允许为空。

**行为约束：**

- 选填，但**建议必填**（尤其对 IN_PROGRESS 任务），用于统一团队对"任务完成"的理解。
- 每条 deliverable 可附带状态（如 `pending` / `done`），用于跟踪部分完成情况。
- 任务标记为 DONE 前，可强制校验 deliverable 是否已全部标记为 done（具体策略待团队讨论）。
- deliverable 可包含链接（如 Figma 地址、文档链接、PR 链接），便于直接访问。

**举例：**

- 任务"上线支付功能"，`deliverable` 填写：
  ```
  [
    {"name": "支付模块 PR", "link": "https://github.com/.../PR/123", "status": "done"},
    {"name": "测试用例覆盖", "link": "", "status": "done"},
    {"name": "上线清单 CheckList", "link": "https://notion.so/...", "status": "pending"}
  ]
  ```
- 三个交付物中仍有 pending 项时，任务不可标记为 DONE（若开启强制校验）。

## 附录：字段与状态机联动汇总

| 字段 | 影响状态 | 联动说明 |
|---|---|---|
| `depends_on` | → IN_PROGRESS | 依赖未 DONE 时禁止进入 IN_PROGRESS |
| `blocked_by` | ↔ BLOCKED | BLOCKED 时建议填写，解除时清空 |
| `priority` | 无直接强制 | 影响调度排序和资源倾斜 |
| `due` | 无直接强制 | 逾期时界面提示，不阻塞状态机 |
| `stage` | 无直接强制 | 纯描述性，用于看板分组展示 |
| `handoff_notes` | 无直接强制 | 协作信息传递，不参与调度 |
| `deliverable` | → DONE | 可选开启"DONE 前必须完成所有 deliverable"校验 |

2. deliverable 是否开启 DONE 前强制全部完成校验？
