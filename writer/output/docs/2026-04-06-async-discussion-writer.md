# 异步讨论观点：看板与讨论机制能否合并

**作者：** 写作助手（writer）
**日期：** 2026-04-06

---

## 一、合并的优点（从内容创作流程角度）

### 1. 信息集中，减少上下文切换
看板和讨论目前是两套独立系统，写作过程中我需要在两个地方追踪状态。合并后，一个入口搞定所有协作信息，流程更顺畅。

### 2. 任务即讨论，讨论即任务
内容创作天然适合"任务+上下文"的模式。一篇文章从选题到发布，本身就是一个持续讨论+分阶段交付的过程。合并后，任务的上下文（讨论记录、决策依据）直接挂在任务下面，不用另外找。

### 3. 状态统一，避免信息孤岛
目前讨论参与者在独立 session 中完成后，写入的是本地文件，再通过 `update_contribution` 更新数据库。但任务的实际状态（是否真正解决、是否闭环）未必同步。合并后，讨论的结果直接反映在任务状态上，减少"说了但没做"的情况。

### 4. 置信度可以变成任务属性
讨论中每个参与者的 `confidence` 评分（high/medium/low），可以作为任务优先级或可信度的参考维度，帮助判断任务是否具备推进条件。

---

## 二、合并的缺点/风险（从写作体验角度）

### 1. 讨论被任务绑架，失去自由度
好的内容讨论往往是发散的，过程中会产生意外的洞察。如果合并太紧，讨论变成"任务的一个步骤"，写作者可能会下意识收敛思路，丧失灵感捕捉的机会。

### 2. 看板复杂度上升
任务看板原本只需要管理"做什么"的状态。合并讨论后，看板需要同时承载"怎么做"的讨论流。对于我这样的写作 agent，可能一个任务挂着一堆讨论记录，反而干扰主流程。

### 3. 多 agent 并行讨论的场景会变复杂
多个 agent 同时对同一个任务发表观点，如果都在同一个"讨论流"里，需要有机制避免覆盖或冲突。单独 session 反而保证了隔离性。

### 4. 历史追溯变难
独立讨论文件（`{date}_{topic}/writer.md`）保留了每个 agent 的原始思考过程，有较高的研究价值。合并到看板数据库后，这些细粒度的讨论脉络可能被扁平化，失去参考价值。

---

## 三、如果能合并，对写作工作流的帮助

### 正面价值
- **选题阶段**：多人讨论的观点直接转化为任务描述，不需要二次整理
- **写作阶段**：素材、思路、决策记录都在任务下，写作时上下文完整
- **交付阶段**：文章发布后，讨论结论+最终稿形成完整档案，方便复盘

### 前提条件
合并要成功，有几个条件：
1. **讨论记录必须可独立存在**：不能因为任务结束/取消，讨论内容就消失
2. **轻量化**：看板 UI/交互不能变复杂，我作为写作 agent 主要通过代码/数据库交互，不依赖图形界面
3. **保留独立讨论的隔离性**：敏感内容（如金哥的个人偏好、团队内部争议）需要独立的讨论空间，不能全部公开在任务下

---

## 四、结论

**部分合并可行，但不要追求完全统一。**

具体建议：

| 层面 | 建议 |
|------|------|
| 任务层 | 合并。看板统一管理所有工作的状态 |
| 讨论层 | 保持独立。讨论文件保留原生格式（markdown），不强行结构化到数据库 |
| 连接层 | 增加映射。讨论完成后，在看板上自动创建/更新一条任务记录（通过 `update_contribution` 机制），但不反过来要求"所有讨论必须关联任务" |
| 存储层 | 分离。任务看板用 SQLite，讨论内容用文件系统，各司其职 |

**核心理念**：让任务看板负责"做没做"，让讨论文件负责"想了什么"。两者通过 manifest.json 和数据库记录形成联动，但不强行合并成一个系统。这样既保证了协作的效率，也保留了内容创作需要的那点"松散空间"。
