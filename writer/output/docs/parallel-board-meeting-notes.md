# 并行看板设计方案会议记录

**日期：** 2026-04-02
**参与人：** dev / writer / finance / community / 小金
**记录人：** writer

---

## 一、问题发现

**背景：** 现有 SQLite 看板状态机为 `PENDING → IN_PROGRESS → BLOCKED → DONE / CANCELLED`，依赖关系靠人工维护。

**核心问题：** 任务 A 完成后，依赖 A 的任务 B 仍停留在 BLOCKED 状态，需要人工解锁才能重新 claim，系统无法自动判断"当前依赖是否已满足"。

> 例如：任务 B 依赖任务 A，当 A 完成时，B 需要人工操作才能继续，而不是系统自动放行。

**结论：** 现有机制是"线性阻塞"模式，不支持并行依赖管理。

---

## 二、第一轮讨论：三种方案及投票

### 方案提出

| 方案 | 描述 | 提出方 |
|------|------|--------|
| 方案1 | 加 `depends_on` 字段，构成 DAG（有向无环图），claim 前做依赖检查 | writer |
| 方案2 | fan-out 自动触发：上游完成后自动激活下游所有依赖方 | dev |
| 方案3 | 阶段分组：按阶段（Phase 1/2/3）划分任务，同组内可并行，不同阶段串行 | community |

### 投票结果

| 参与者 | 倾向 |
|--------|------|
| dev | 方案1 |
| writer | 方案1 |
| finance | 方案1 |
| community | 方案3 |
| 小金 | 方案1 |

**结论：** 4:1，方案1（DAG + depends_on）获得主导方向，方案3保留作为备选讨论。

---

## 三、第二轮讨论：讨论质量问题暴露

**问题：** 随着讨论深入，各人对"方案1"的理解出现了分歧——

- **dev** 指出：有人理解的 DAG 是"每个任务只能有一个依赖"，但真正的 DAG 是"一个任务可以有多个依赖"；还有人把"fan-out 自动触发"和"DAG 字段"混为一谈。
- **finance** 补充：字段粒度不同会直接影响后续统计和审计逻辑。
- **community** 重申：方案3的阶段分组更直观，适合非技术成员理解。

**核心矛盾：**
- 各人对"什么是 DAG"、"depends_on 字段应该存什么"理解不一致
- 方案2（fan-out）和方案1（DAG）存在功能边界的混淆
- 没有人明确定义 claim 的前置条件是什么

**结论（dev 主导）：**
暂停投票，先统一定义：
1. depends_on 字段语义：存被依赖任务的 ID 列表
2. claim 前置条件：所有 depends_on 中的任务必须处于 DONE 状态
3. 阶段分组作为视图层辅助，不影响核心数据模型

## 四、草案制定：7个字段定义

writer 起草，dev 技术审查，最终字段定义如下：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `id` | string | 任务唯一标识 |
| `title` | string | 任务标题 |
| `status` | enum | PENDING / IN_PROGRESS / DONE / CANCELLED |
| `depends_on` | string[] | **被依赖任务 ID 列表**（即：本任务等待哪些任务完成） |
| `blocked_by` | string[] | **阻塞本任务的任务 ID 列表**（由系统反向推导，或由人工维护） |
| `priority` | int | 优先级（数值越小优先级越高） |
| `deliverable` | string | 交付物描述（用于校验是否真正完成） |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

**dev 技术审查意见：**
- `blocked_by` 与 `depends_on` 存在数据冗余，建议合并或明确单向维护职责
- `deliverable` 字段需要配合校验规则，否则只是占位符
- `priority` 需要定义抢锁逻辑：当高优先级任务 claim 时，低优先级正在 IN_PROGRESS 的任务是否退让？

**结论：** 字段定义 V1 完成，`blocked_by` 合并问题、deliverable 校验规则、priority 抢锁逻辑留待方案锁定阶段投票决定。

## 五、方案锁定：四个待确认问题投票

### 问题 1：硬拦截 vs 软提示

当 claim 时依赖未满足，系统应该：
- **硬拦截**：直接拒绝 claim，返回错误
- **软提示**：允许 claim，但弹出警告并记录

| 参与者 | 立场 |
|--------|------|
| dev | 硬拦截 |
| writer | 硬拦截 |
| finance | 硬拦截 |
| community | 软提示 |
| 小金 | 软提示 |

**结论：** 硬拦截胜出（3:2）。理由：硬拦截能保证数据一致性，软提示容易产生"幽灵任务"（名义上 claim 了但实际被真实依赖卡住）。

---

### 问题 2：deliverable 校验规则

任务标记 DONE 前，是否必须填写/校验 deliverable？

| 参与者 | 立场 |
|--------|------|
| dev | 必须填写，且内容长度 ≥ 10 字符 |
| writer | 必须填写，但长度不限 |
| finance | 必须填写，且需关联金额字段（如有） |
| community | 建议填写，不强制 |
| 小金 | 必须填写，且需上传附件 |

**结论：** MVP 版本采用"必须填写 deliverable + 最低字符数限制（10字符）"，附件和金额关联作为后续迭代需求。

---

### 问题 3：blocked_by 字段是否合并

`depends_on`（正向依赖）和 `blocked_by`（反向阻塞）是否存在冗余？

**立场：**
- **dev / writer**：不合并，`blocked_by` 保留用于"谁在等我"的视图查询，物理冗余但逻辑清晰
- **finance**：合并，只保留 `depends_on`，`blocked_by` 由系统实时推导
- **community / 小金**：无所谓，看实现复杂度

**结论：** MVP 阶段**不合并**，`blocked_by` 作为只读派生字段由系统维护，不允许人工写入。这样既保证查询效率，又避免数据不一致。

---

### 问题 4：handoff（交接）审计

任务从一人转交给另一人时，是否需要记录审计日志？

| 参与者 | 立场 |
|--------|------|
| dev | 需要，记录转移前后的 user_id 和时间戳 |
| writer | 需要，且需记录转移原因 |
| finance | 必须，关联财务审批流 |
| community | 简单记录即可 |
| 小金 | 需要，且记录在任务评论中 |

**结论：** MVP 版本记录 `handoff_user_id`（转移给谁）和 `handoff_at`（转移时间），转移原因作为可选字段，财务关联审批流作为后续需求。

## 六、边界场景讨论

### 场景 1：环形依赖（A 依赖 B，B 依赖 A）

**讨论：** 系统检测到环形时如何处理？

**结论：**
- claim 时做 DFS 环形检测
- 发现环形 → 拒绝 claim，并提示"检测到循环依赖，请检查任务链"
- 环形检测在 claim 时触发，不在写入时触发（避免每次编辑都要检测）

---

### 场景 2：多并发 claim（两个用户同时 claim 同一个任务）

**讨论：** 同一任务被两个用户同时发起 claim，如何处理？

**结论：**
- 引入 **Lease claim 机制**（乐观锁 + TTL）
- claim 时设置 lease_expires_at（如：5分钟后过期）
- claimer 需要在 TTL 内续约，否则自动释放
- 多并发时：先到先得，后续 claim 返回"任务已被 claim，请稍后重试"

---

### 场景 3：跨阶段任务依赖

**讨论：** 阶段分组（方案3）下，不同阶段的任务是否可以互相依赖？

**结论：**
- **允许跨阶段依赖**，阶段分组仅为可视化分区，不做强制约束
- 系统按实际 DAG 依赖关系判断 claim 资格
- 阶段视图需支持"跨阶段依赖"的视觉连线

---

### 场景 4：依赖链中途删除

**讨论：** 任务 A 在 DONE 后被删除，依赖 A 的任务 B 怎么办？

**结论：**
- DONE 状态的任务不允许删除（软删除也不行），需先撤销 DONE 状态
- 如果 B 已经 IN_PROGRESS 且依赖链失效 → 允许 B 继续完成，但记录一条警告日志
- 系统在 B claim 时检查依赖是否仍然存在，不存在则提示用户确认

---

### 场景 5：优先级抢占

**讨论：** 高优先级任务能否抢占低优先级任务的 IN_PROGRESS 槽位？

**结论：**
- **不主动抢占**，高优先级任务只能等待低优先级任务自然释放（完成或主动放弃）
- 但可以在看板视图中高亮显示"有高优先级任务在等待此任务完成"
- 避免强制抢占带来的工作状态损坏

## 七、外部调研：四个领域成熟方案

writer 进行了外部调研，搜索了以下四个领域的并行/依赖管理方案：

| 领域 | 代表系统/工具 | 关键机制 |
|------|-------------|----------|
| 技术领域 | GitHub Actions、Airflow、Temporal | DAG + 状态机 + 重试队列 |
| 产品 UX | Linear、Jira、Notion | depends_on + 可视化依赖图 + 阻塞提示 |
| 金融系统 | 分布式事务、Saga 模式 | 补偿事务 + 最终一致性，不走强阻塞 |
| 内容运营 | Airtable、Asana、Nova | 阶段分组 + 成员分配 + 自动化触发（fan-out） |

**调研结论：**
- 技术领域方案最成熟，可以直接借鉴 DAG + 状态机 + lease claim 模式
- 产品 UX 方案的用户体验值得参考（特别是阻塞提示和依赖可视化）
- 金融系统方案提供了一条"不用硬拦截"的思路，但本次 MVP 不采用
- 内容运营方案的 fan-out 触发逻辑可以作为后续自动化场景的扩展点

## 八、最终方案

### 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 主数据库 | SQLite | 现有基础设施，MVP 够用 |
| 依赖索引 | Redis Sorted Set | 用 ZSET 存储每个任务的依赖集合，支持 O(1) 命中判断 |
| 环形检测 | DFS | claim 时遍历依赖链，检测闭环 |
| claim 机制 | Lease claim + TTL | 乐观锁 + 过期释放，防多并发抢锁 |
| 任务排队 | 队首插入 | 高优先级任务插入队首，优先调度 |

### 最终字段定义（V2，已锁定）

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `id` | string | 任务唯一标识 |
| `title` | string | 任务标题 |
| `status` | enum | PENDING / IN_PROGRESS / DONE / CANCELLED |
| `depends_on` | string[] | 本任务依赖的任务 ID 列表 |
| `blocked_by` | string[] | 由系统维护，只读派生（不合并进 MVP） |
| `priority` | int | 优先级（数值越小越高） |
| `deliverable` | string | 交付物描述（claim DONE 前必须填写，≥10字符） |
| `assigned_to` | string | 当前负责人 user_id |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |
| `lease_expires_at` | datetime | claim TTL 过期时间（null = 未 claim） |

### MVP 范围（V1）

**包含：**
- `depends_on` 字段 + claim 前依赖检查（硬拦截）
- DFS 环形依赖检测
- Lease claim + TTL（5分钟）
- `deliverable` 必须填写（≥10字符）
- `blocked_by` 只读派生字段（系统维护，不人工写入）
- Handoff 审计：记录 `handoff_user_id` 和 `handoff_at`
- 队首插入调度（高优先级先调度）
- 不主动抢占正在 IN_PROGRESS 的任务

**不包含（后续迭代）：**
- `blocked_by` 与 `depends_on` 完全合并
- deliverable 附件上传
- 财务金额关联
- fan-out 自动触发
- 阶段分组视图（作为辅助展示保留，不做强制约束）

## 九、Dev Review 后发现的三个实现问题

> 以下问题由 dev 在 Review 会议记录时提出，需在 MVP 落地前确认：

### 问题 A：Lease 过期后的状态回滚未定义

**现状：** MVP 包含 Lease claim + TTL（5分钟），但没有定义：任务在 IN_PROGRESS 时 lease 过期，是自动回滚到 PENDING，还是需要人工操作？

**风险：** 如果 lease 过期后任务仍占用槽位，可能导致高优先级任务等待时死锁。

**建议：** Lease 过期自动释放，回滚至 PENDING，不占用槽位。

**待确认：** 接受这个方案还是需要人工介入？

---

### 问题 B：Handoff 缺少转让人字段

**现状：** MVP 记录 `handoff_user_id`（转移给谁）和 `handoff_at`（转移时间），但没有记录 `handoff_from_user_id`（从谁转出）。

**风险：** 审计链路不完整，接收方看到的历史是断的。

**建议：** 加一个 `handoff_from_user_id` 字段即可解决，字段加在 handoff_audit 表里。

**待确认：** 接受加字段还是另有方案？

---

### 问题 C：`blocked_by` 的实际用途未明确

**现状：** MVP 把 `blocked_by` 定义为"只读派生字段"，但没说清 claim 时是否参考这个字段。如果 claim 只看 `depends_on`，`blocked_by` 在 MVP 阶段实际上没有作用。

**建议：** MVP 阶段直接去掉 `blocked_by` 字段，只保留 `depends_on`，避免给实现和理解增加复杂度。

**待确认：** 保留 `blocked_by` 并明确其用途，还是 MVP 先去掉？
